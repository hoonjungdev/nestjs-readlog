# 04. e2e 테스트와 전역 파이프

- 날짜: 2026-08-12
- 관련 커밋: `9323112`

## 무엇을 만들었나

3단계 끝에 남겨뒀던 숙제를 처리했다.

1. `ValidationPipe` 설정을 `main.ts`에서 `AppModule`로 옮겨, e2e 테스트도 실제 서버와 **같은 검증**을 거치게 했다.
2. 검증 실패, PATCH, DELETE에 대한 e2e 테스트 7개를 추가했다 (6개 → 13개).

## 왜 필요했나

3단계 노트에 이렇게 적어뒀다.

> 현재 e2e 테스트는 `ValidationPipe`를 전혀 거치지 않는다.
> "테스트가 통과한다"가 "실제 서버에서도 그렇게 동작한다"를 의미하지 않는 경우다.

이번엔 그걸 **테스트로 증명**하는 것부터 시작했다. 검증이 걸린다면 400이어야 할 요청 두 개를 테스트로 적고 돌렸다.

```text
● /reading-records (POST) returns 400 when a required field is missing
  expected 400 "Bad Request", got 201 "Created"

● /reading-records (POST) returns 400 for an unknown field
  expected 400 "Bad Request", got 201 "Created"
```

기존 6개는 그대로 통과하는데 새로 쓴 2개만 실패했다. **테스트가 늘어난 게 아니라, 원래 뚫려 있던 구멍이 이제 보이게 된 것이다.**

## 핵심 개념 — 내 말로 다시 쓰기

### 1. 설정을 앱 밖에 두면 환경이 갈라진다

이번 문제의 뿌리는 이 그림 하나로 설명된다.

```text
실제 서버:  main.ts (bootstrap)          ← ValidationPipe가 여기 있었다
              └─ AppModule ─ Controller ─ Service

e2e 테스트:  (main.ts를 실행하지 않음)
              └─ AppModule ─ Controller ─ Service     ← 파이프 없음
```

`app.useGlobalPipes()`는 `bootstrap()` **함수 안의 한 줄**이다. 테스트는 `AppModule`만 가져다 앱을 만들기 때문에 그 줄이 실행될 일이 애초에 없었다.

여기서 배운 규칙:

> **앱의 동작을 결정하는 설정은 앱을 부팅하는 코드가 아니라 앱 자체(모듈)에 두어야 한다.**

`main.ts`에만 있는 설정은 "실제로 서버를 띄웠을 때만 존재하는 동작"이 된다. 테스트는 그걸 볼 수 없다.

### 2. `APP_PIPE` — 약속된 이름표

해결책은 파이프를 `AppModule`의 프로바이더로 등록하는 것이었다.

```ts
providers: [
  AppService,
  {
    provide: APP_PIPE,
    useValue: new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
    }),
  },
],
```

`APP_PIPE`는 `@nestjs/core`가 미리 정해둔 **약속된 이름표(토큰)** 다. 이 이름표를 달아 프로바이더를 등록하면 Nest가 "이건 그냥 서비스가 아니라 전역 파이프구나" 하고 알아보고 모든 라우트에 적용한다.

형제가 셋 더 있다. 하는 일만 다르고 등록 방식은 똑같다.

| 토큰 | 언제 도는가 |
| --- | --- |
| `APP_PIPE` | 요청 데이터를 변환·검증할 때 |
| `APP_GUARD` | 요청을 허용할지 말지 결정할 때 (인증/권한) |
| `APP_INTERCEPTOR` | 요청 전후를 감쌀 때 (로깅, 응답 가공) |
| `APP_FILTER` | 예외가 터졌을 때 응답으로 바꾸는 곳 |

`main.ts`에서는 `useGlobalPipes()`를 지웠다. 남겨두면 같은 검증이 두 번 돈다.

### 3. `useValue` vs `useClass`

프로바이더를 등록하는 방법이 여러 가지라는 걸 처음 알았다.

| 문법 | 하는 일 | 언제 |
| --- | --- | --- |
| `useClass: ValidationPipe` | Nest가 클래스를 **직접 인스턴스화** | 생성자 인자가 필요 없을 때 |
| `useValue: new ValidationPipe({...})` | **내가 만든 인스턴스**를 그대로 사용 | 옵션을 넘겨야 할 때 |

여기서는 `whitelist`, `forbidNonWhitelisted` 옵션을 넘겨야 했다. `useClass`는 Nest가 알아서 `new`를 호출하므로 옵션을 끼워 넣을 자리가 없다. 그래서 `useValue`를 썼다.

### 4. 전역 파이프의 영향 범위 — 무엇이 바뀌고 무엇이 그대로인가

| | 이전 | 이후 |
| --- | --- | --- |
| 실제 서버에 적용되나 | ✅ | ✅ (그대로) |
| 적용 범위 | 앱 전체 | 앱 전체 (그대로) |
| **e2e 테스트에 적용되나** | ❌ | ✅ **달라진 부분** |
| 설정이 적힌 곳 | `main.ts` | `app.module.ts` |

동작 범위 자체는 넓어지지 않았다. 바뀐 건 **"AppModule을 쓰는 모든 곳"이 자동으로 같은 설정을 얻는다**는 점이다.

대신 대가가 하나 있다. `main.ts`만 읽어서는 파이프가 어디 있는지 안 보인다. 그래서 `main.ts`에 주석을 한 줄 남겼다.

### 5. 단위 테스트와 e2e 테스트는 서로를 대신하지 못한다

같은 버그를 두 계층에서 봤더니 **다른 모습**으로 보였다.

| | 단위 테스트 | e2e 테스트 |
| --- | --- | --- |
| 무엇을 거치나 | 서비스 함수만 직접 호출 | HTTP → 파이프 → 컨트롤러 → 서비스 |
| 파이프가 도나 | ❌ | ✅ |
| 잡을 수 있는 것 | 비즈니스 규칙 | 상태 코드, 검증, 응답 형태 |
| 놓치는 것 | 파이프가 값의 모양을 바꾸는 문제 | 세밀한 분기 |

3단계에서 겪은 `Object.assign` 버그가 딱 이 경계에 있었다. 단위 테스트는 파이프를 안 거쳐서 처음에 못 잡았고, e2e는 그때 검증이 안 걸려 있어서 못 잡았다. **양쪽 다 뚫려 있었던 셈이다.**

## 이번 단계에 쓴 문법 — 빠른 참조

### supertest

| 문법 | 하는 일 |
| --- | --- |
| `request(app.getHttpServer())` | 테스트용 앱의 HTTP 서버로 요청 시작 |
| `.post('/path').send({...})` | 본문을 담아 요청 |
| `.expect(400)` | **상태 코드** 단언 |
| `.expect({ id: 1, ... })` | **응답 본문 전체** 단언 (부분 일치 아님) |

`.expect()`는 인자 타입에 따라 검사 대상이 달라진다. 숫자면 상태 코드, 객체면 본문이다.

### 전역 프로바이더

| 문법 | 하는 일 |
| --- | --- |
| `provide: APP_PIPE` | 이 프로바이더가 전역 파이프임을 Nest에 알림 |
| `useValue: <인스턴스>` | 내가 만든 인스턴스를 그대로 제공 |
| `useClass: <클래스>` | Nest가 대신 인스턴스화 |

## 막혔던 지점 ⭐

### 같은 버그가 계층에 따라 다르게 보인다

PATCH 회귀 테스트가 **정말로** 3단계의 버그를 잡는지 확인하려고, 서비스를 일부러 옛날 코드로 되돌려봤다.

```ts
Object.assign(readingRecord, updateReadingRecordDto);   // 버그 버전
```

```text
● /reading-records/:id (PATCH) updates only the given fields

  expected { id: 1, title: '클린 코드', author: 'Robert C. Martin' } response body,
  got      { id: 1, author: 'Robert C. Martin' }
```

의도대로 **이 테스트 하나만** 실패했다. 여기까진 예상대로였는데, 실패 메시지를 보고 어? 했다.

3단계 단위 테스트에서는 이렇게 보였었다.

```text
Expected: "클린 코드"
Received: undefined        ← title 키는 있고 값이 undefined
```

그런데 e2e에서는 `title` **키 자체가 응답에 없다.**

```text
got { id: 1, author: 'Robert C. Martin' }     ← title이 통째로 사라짐
```

이유를 확인해봤다.

```bash
node -e 'console.log(JSON.stringify({ id: 1, title: undefined, author: "x" }))'
# {"id":1,"author":"x"}
```

`JSON.stringify`는 **값이 `undefined`인 속성을 아예 버린다.** 객체 안에는 `title: undefined`가 분명히 있는데, JSON으로 바뀌는 순간 없어진 것처럼 보인다.

배운 것:

- **메모리 안의 객체와 클라이언트가 받는 JSON은 같지 않다.** 그 사이에 직렬화라는 변환이 한 번 더 있다.
- 그래서 같은 버그라도 단위 테스트에서는 "값이 `undefined`", e2e에서는 "필드가 없음"으로 나타난다.
- 앞으로 nullable 필드를 다룰 때 조심해야 할 지점이다. `undefined`는 응답에서 사라지지만 `null`은 `"key": null`로 남는다. **둘을 구분해서 결정해야 한다.**

### 회귀 테스트는 실패를 확인해야 의미가 있다 (두 번째)

3단계에서 배운 걸 이번에도 그대로 했다. 새 테스트 7개 중 3개(검증 2개 + PATCH 회귀 1개)는 **의도한 대로 실패하는 것을 눈으로 본 다음** 고쳤다.

나머지 4개(PATCH 404, PATCH 400, DELETE 204→404, DELETE 404)는 처음부터 통과했다. 이건 "이미 잘 되던 동작을 앞으로도 지키겠다"는 의미의 테스트라 성격이 다르다. 두 종류를 구분해서 생각하게 됐다.

| 성격 | 언제 쓰나 | 실패를 봐야 하나 |
| --- | --- | --- |
| 회귀 테스트 | 이미 터진 버그를 다시 못 터지게 | **반드시** — 안 그러면 아무것도 검사 안 하는 테스트일 수 있음 |
| 계약 테스트 | 현재 동작을 문서처럼 고정 | 아니오 (처음부터 통과가 정상) |

```bash
pnpm build
```
