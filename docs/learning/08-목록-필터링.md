# 08. 목록 조회 — 필터링, 페이지네이션, 응답 타입 분리, 정렬

- 날짜: 2026-08-20 ~ 2026-08-22
- 관련 커밋: `e032728` (상태 필터), `d2f2aac` (페이지네이션), `aa52218` (응답 타입 분리),
  `757f4ac` (e2e 테스트), `b0135bb` (정렬)

## 무엇을 만들었나

`GET /reading-records`에 `?status=reading`처럼 쿼리 파라미터로 상태별 필터링을 추가했다.
파라미터가 없으면 지금까지처럼 전체를 반환한다.

이어서 `?page=`, `?limit=`로 목록을 잘라서 반환하는 페이지네이션을 추가했다. 응답 모양은
배열이 아니라 `{ data, total, page, limit }` 객체로 바꿨다 — `total`(조건에 맞는 전체 개수)이
없으면 클라이언트가 "마지막 페이지인지"를 알 방법이 없기 때문이다.

응답 전용 타입 `ReadingRecordResponseDto`를 만들어 Prisma 엔티티와 분리했다.
서비스의 모든 메서드가 `toResponse()`를 거쳐 이 타입으로 옮겨 담아 반환한다.

마지막으로 `?sort=title&order=desc` 정렬을 추가했다. 정렬 가능한 컬럼은 허용 목록으로 제한했다.

## 왜 필요했나

지금까지 `findAll()`은 항상 테이블 전체를 반환했다. "읽는 중인 책만 보고 싶다"는 요구를
지금은 클라이언트가 전체를 받아서 직접 걸러야 하는데, 데이터가 늘수록 낭비가 커진다.
거를 수 있는 쪽(DB)에서 거르도록 옮겼다.

필터링만으로는 부족했다. 상태 필터를 걸어도 여전히 "그 상태에 맞는 행 전부"가 한 번에
돌아온다. 기록이 수백 건이 되면 응답이 커지고 느려지므로, 한 번에 몇 건만 잘라서 주는
방법이 필요했다.

응답 전용 타입은 성격이 좀 다르다. 로드맵의 표현도 "분리하기"가 아니라 **"분리할지 판단하기"**였고,
지금 `ReadingRecord`의 다섯 필드는 전부 공개해도 되는 값이라 **당장 숨길 게 하나도 없었다.**
그런데도 분리하기로 한 이유는 "노출의 방향" 때문이다. 엔티티를 그대로 반환하면
`schema.prisma`에 컬럼을 추가하는 것만으로 그 값이 코드 수정 없이 응답에 나간다(opt-out).
나중에 로그인을 붙여 `userId` 같은 필드가 생길 때 실수로 새는 걸 막아주는 장치가 없다는 뜻이다.
대신 대가도 분명하다 — 공개할 필드를 추가할 때 고쳐야 할 곳이 한 곳에서 세 곳으로 늘었다.

## 핵심 개념 — 내 말로 다시 쓰기

- **`@Query()`**: `@Body()`가 요청 본문을 꺼내듯, URL의 `?key=value` 부분을 꺼내는 데코레이터다.
  같은 자리에서 전역 `ValidationPipe`가 그대로 적용된다.
- **DTO 클래스 없이 개별 값만 꺼내면 `class-validator`가 동작하지 않는다.**
  `@Query('status') status: ReadingStatus`처럼 타입만 붙이면 `tsc`는 통과하지만, 그 타입은
  실행 중엔 사라지는 컴파일 시점 정보라서 `@IsEnum` 같은 런타임 검증이 전혀 걸리지 않는다.
  `@Query() query: FindReadingRecordsDto`로 DTO 전체를 받아야, 그 클래스에 붙은 데코레이터가
  실제로 실행된다.
- **`where`절의 `undefined` 규칙**: Prisma의 `create()`에서 `data`에 넘긴 필드가 `undefined`면
  그 컬럼이 INSERT문에서 빠지는 것처럼, `findMany()`의 `where`에서도 `where: { status: undefined }`는
  그 조건이 아예 없는 것과 동일하게 동작한다. `if` 분기로 조건 객체를 조립할 필요가 없다.
- **`skip` / `take`**: SQL의 `OFFSET` / `LIMIT`에 대응하는 Prisma 옵션. `page=2, limit=10`이면
  `skip: (page - 1) * limit, take: limit`으로 변환한다. 몇 번째 행부터(`skip`) 몇 개를(`take`)
  가져올지를 뜻한다.
- **`count()`는 `findMany()`와 별개의 쿼리**: "일부 데이터 + 전체 개수"를 한 번의 쿼리로 얻는 방법은
  없다. `total`이 필요하면 `count()`를 따로 호출해야 한다. 서로 의존하지 않는 두 쿼리라
  `Promise.all([findMany(...), count(...)])`로 동시에 보내서 순서대로 기다리는 시간을 없앴다.
- **쿼리 파라미터의 문자열→숫자 변환은 자동이 아니다**: URL 쿼리는 항상 문자열(`"1"`)로 온다.
  숫자로 바꿔주는 건 `class-transformer`의 `@Type(() => Number)`다. 이게 없으면 `page`는
  `"2"`인 채로 응답까지 나간다. (전역 `ValidationPipe`의 `transform: true`도 관련이 있는데,
  생각했던 것과 역할이 달랐다 — 아래 "막혔던 지점" 참고)
- **`sort`는 지금까지 받은 파라미터와 종류가 다르다**: `status`나 `page`는 "값(데이터)"이지만
  `sort`는 **쿼리의 구조**, 즉 컬럼 이름 자체를 사용자가 정하는 것이다. 그래서 허용 목록이
  선택이 아니라 필수다. (아래 "막혔던 지점"에서 실제로 확인)
- **`as const`와 `(typeof X)[number]`**: 배열에 `as const`를 붙이면 타입이 `string[]`이 아니라
  `readonly ['id', 'title', ...]`로 좁혀지고, `[number]`로 그 원소들의 유니온 타입을 꺼낼 수 있다.
  값 목록(런타임 검증용)과 타입(컴파일 검사용)을 **한 곳에서** 얻는 방법이다.

## 이번 단계에 쓴 문법 — 빠른 참조

| 문법 | 하는 일 | 예시 |
| --- | --- | --- |
| `@Query()` | URL 쿼리 파라미터 전체를 DTO로 받음 (ValidationPipe 적용됨) | `@Query() query: FindReadingRecordsDto` |
| `@Query('key')` | 쿼리 파라미터 하나만 꺼냄 — DTO를 거치지 않으므로 검증이 안 걸림 | `@Query('status') status?: string` |
| `@Type(() => Number)` | 값을 검증 전에 지정한 타입으로 변환 (문자열 → 숫자) | `@Type(() => Number) page: number` |
| `skip` / `take` | `findMany()`에서 건너뛸 개수 / 가져올 개수 (OFFSET/LIMIT) | `{ skip: 10, take: 10 }` |
| `count()` | `where` 조건에 맞는 행의 개수만 셈 (데이터는 안 가져옴) | `prisma.readingRecord.count({ where })` |
| `Promise.all([...])` | 서로 독립적인 여러 프로미스를 동시에 실행하고 모두 끝나길 기다림 | `const [a, b] = await Promise.all([p1, p2])` |
| 초과 속성 검사 | 객체 리터럴에 **직접 적은** 속성이 타입에 없으면 오류 (스프레드는 검사 안 함) | `return { id, nope: 1 }` → TS2353 |
| `Object.keys(obj)` | 객체의 키 이름을 문자열 배열로 반환 — 응답 모양을 테스트로 못박을 때 씀 | `Object.keys(r).sort()` |
| `@IsIn([...])` | 값이 그 배열 안에 있는지 실행 중에 확인 | `@IsIn(SORTABLE_FIELDS) sort: SortableField` |
| `as const` | 배열/객체 리터럴의 타입을 리터럴 그대로 좁힘 (넓히기 방지) | `['id', 'title'] as const` |
| `(typeof X)[number]` | 배열 타입에서 원소들의 유니온 타입을 꺼냄 | `type F = (typeof FIELDS)[number]` |
| `orderBy` | `findMany()`의 정렬 조건. `{ 컬럼: 'asc' \| 'desc' }` | `orderBy: { title: 'desc' }` |

## 막혔던 지점 ⭐

처음엔 컨트롤러에서 `@Query('status') status?: ReadingStatus`로 값을 개별로 꺼냈다.
`tsc --noEmit`과 `pnpm lint` 둘 다 통과해서 겉으로는 문제가 없어 보였다.

그런데 이건 `FindReadingRecordsDto`에 붙여둔 `@IsEnum(ReadingStatus)`가 **전혀 실행되지 않는**
상태였다. `class-validator`의 데코레이터는 "DTO 클래스의 인스턴스"에 붙어 있어야 `ValidationPipe`가
그 인스턴스를 검사하는데, `@Query('status')`로 값만 뽑아내면 그 DTO 클래스 자체를 거치지 않으니
데코레이터가 있어도 아무 의미가 없다.

`status?: ReadingStatus`라는 타입 표기는 컴파일할 때만 존재하고 실행 중엔 완전히 사라진다.
그래서 타입을 아무리 좁게 써도 `?status=땅콩` 같은 잘못된 값이 그대로 서비스, Prisma까지
넘어갈 뻔했다 (`update()`에서 `findOne()`을 먼저 안 부르면 Prisma의 `P2025`가 새어 나가 500이
되는 것과 같은 패턴 — 검증되지 않은 값이 프레임워크 경계를 넘어가면 의도한 400 대신 다른 에러로
바뀐다).

고친 방법은 `@Body()`에서 이미 쓰던 패턴과 완전히 같았다: `@Query() query: FindReadingRecordsDto`로
DTO 전체를 받고, `query.status`를 서비스에 넘기는 것.

### 정렬: "SQL 주입이 되나?"를 직접 확인해 봤다

`?sort=title`처럼 **컬럼 이름을 사용자가 보내는** 건 처음이라, 검증을 빼면 실제로 무슨 일이
일어나는지 궁금했다. `@IsIn`을 잠깐 떼고 요청을 보내 봤다.

```bash
curl "http://localhost:3001/reading-records?sort=password"
# {"statusCode":500,"message":"Internal server error"}

curl "http://localhost:3001/reading-records?sort=id%3B%20DROP%20TABLE%20reading_records%3B"
# {"statusCode":500,"message":"Internal server error"}
```

둘 다 500이고, 테이블은 멀쩡했다. Prisma가 던진 오류를 직접 잡아보니
`PrismaClientValidationError`였다 — Prisma는 컬럼 이름을 **SQL 문자열에 끼워 넣지 않고**
쿼리 구조를 먼저 검증해서 거부한다. 그래서 **SQL 주입은 아니다.**

그렇다고 검증이 필요 없는 건 아니었다. 남는 문제가 둘이다.

1. **의도한 400이 아니라 500이 된다.** 잘못된 `status`를 보내면 "이 값은 안 된다"고 알려주는데,
   잘못된 `sort`는 그냥 서버 오류가 된다. 사용자 입력이 원인인데 서버 잘못처럼 보인다.
   (`update()`에서 `findOne()`을 안 부르면 `P2025`가 새어 나가 500이 되던 것과 같은 패턴이다.)
2. **정렬하라고 의도하지 않은 컬럼까지 정렬된다.** 지금은 다섯 컬럼뿐이라 티가 안 나지만,
   컬럼이 늘면 그대로 노출된다.

허용 목록을 `Prisma.ReadingRecordScalarFieldEnum`(Prisma가 만들어주는 전체 컬럼 목록)으로
쓰면 편하겠다고 잠깐 생각했는데, 그러면 컬럼을 추가하는 순간 자동으로 정렬 가능해진다.
**바로 앞 단계에서 응답 전용 타입으로 막았던 opt-out 문제와 완전히 같은 모양이라** 직접 적기로 했다.

### 정렬: `rating` 내림차순의 결과가 예상과 달랐다

`?sort=rating&order=desc`면 5점짜리가 맨 앞일 거라고 생각했는데, **별점이 없는(`null`) 책이
가장 앞에** 왔다. PostgreSQL이 `ORDER BY`에서 `NULL`을 "가장 큰 값"으로 취급하기 때문이다.

지금은 이 동작을 그대로 두되, 테스트로 못박아 뒀다. 바꾸고 싶으면 Prisma의
`{ rating: { sort: 'desc', nulls: 'last' } }`를 쓰면 된다.

### `pnpm test`가 통과해도 e2e는 깨져 있었다

페이지네이션에서 목록 응답을 배열에서 객체로 바꾸고 `pnpm test`(19개)가 통과하는 걸 보고
"다 됐다"고 판단했다. 나중에 e2e 테스트를 손대려고 `pnpm test:e2e`를 돌렸더니 **2개가 실패**하고
있었다. 목록 응답을 배열로 기대하던 기존 테스트들이었다.

```
Error: expected [ ... ] response body, got {
  data: [ ... ], total: 1, page: 1, limit: 10
}
```

두 스위트는 **대상이 다르다.** `pnpm test`는 `package.json`의 jest 설정(`rootDir: "src"`)을 써서
`src/**/*.spec.ts`만 돌리고, `pnpm test:e2e`는 `test/jest-e2e.json`으로 `test/*.e2e-spec.ts`를
돌린다. 즉 `pnpm test`는 `test/` 폴더를 **아예 쳐다보지 않는다.**

응답 형태처럼 HTTP 계약이 바뀌는 변경은 단위 테스트가 잡아주지 못한다. 서비스 반환값의
타입은 바뀌었지만 서비스 테스트는 여전히 `result.data`를 보고 있었으니 통과하는 게 당연했다.
깨진 건 "서비스가 무엇을 돌려주는가"가 아니라 "API가 무엇을 응답하는가"였고, 그건 e2e의 몫이다.

→ **공개 API의 모양을 바꿨으면 `pnpm test`와 `pnpm test:e2e`를 둘 다 돌린다.**

### 응답 전용 타입: 타입 검사에 구멍이 있었다

`toResponse()`의 반환 타입을 `ReadingRecordResponseDto`로 명시하면 컴파일러가 막아준다고 생각했다.
실제로 없는 필드를 적어보니 정말 막혔다.

```
error TS2353: Object literal may only specify known properties,
and 'internalSecret' does not exist in type 'ReadingRecordResponseDto'.
```

그런데 같은 함수를 `return { ...record };`로 바꿔 보니 **오류가 하나도 안 났다.**
이게 '초과 속성 검사(excess property check)'의 범위 때문이다 — 이 검사는 객체 리터럴에
**직접 적은** 속성에만 걸리고, 스프레드(`...`)로 펼쳐 넣은 속성은 검사하지 않는다.
즉 응답 타입을 분리해 놓고도 한 줄 실수로 모든 컬럼이 새어 나갈 수 있는데 `tsc`는 조용하다.

그래서 "무엇이 공개되는가"라는 약속은 타입이 아니라 **런타임 테스트**로 못박아 두기로 했다
(`Object.keys()`로 응답의 키 목록을 비교). 타입 검사와 런타임 검증이 다른 일을 한다는 건
3단계에서 `@IsString()`을 배울 때 이미 나왔던 이야기인데, 이번엔 반대 방향에서 같은 교훈을 만났다.
그때는 "들어오는 값"이었고 이번엔 "나가는 값"이다.

### 페이지네이션: `transform: true`에 대해 처음엔 틀리게 알고 있었다

`page`, `limit`을 추가하면서 `@Type(() => Number)`와 함께 전역 `ValidationPipe`에
`transform: true`를 켰다. 이때 "이 옵션이 없으면 컨트롤러가 문자열을 받는다"고 적어뒀는데,
**나중에 e2e 테스트를 붙이면서 확인해 보니 사실이 아니었다.**

`transform: true`를 주석 처리하고 실제로 요청을 보내 봤더니 `page`는 그대로 숫자로 나왔다.

```
body: {"data":[],"total":0,"page":2,"limit":2}
typeof page: number typeof limit: number
```

`node_modules`의 `validation.pipe.js`를 직접 열어보고 이유를 알았다.

```js
// 생성자 — forbidUnknownValues를 항상 끼워 넣는다
this.validatorOptions = { forbidUnknownValues: false, ...validatorOptions };

// transform이 꺼져 있을 때의 반환 경로
const shouldTransformToPlain = Object.keys(this.validatorOptions).length > 1;
return shouldTransformToPlain
    ? classTransformer.classToPlain(entity, this.transformOptions)
    : value;
```

`transform`이 꺼져 있어도 `validatorOptions`의 키가 1개보다 많으면 **변환이 적용된 인스턴스**를
`classToPlain`으로 되돌려 반환한다. 생성자가 `forbidUnknownValues`를 항상 넣어주므로
`whitelist` 하나만 있어도 키가 2개가 되어 이 조건이 성립한다. 그래서 우리 설정에서는
`transform: true`가 없어도 변환이 됐던 것이다.

그래도 `transform: true`는 남겨두기로 했다. 저 동작은 Nest 내부의 휴리스틱이고
(소스에도 GitHub 이슈 번호를 단 주석이 붙어 있다), 우리가 기대는 계약이 아니기 때문이다.
다만 **주석에 적는 이유를 사실대로 바꿨다.**

교훈이 두 개다.

1. **"이 옵션이 없으면 이렇게 된다"는 설명은 실제로 꺼 보기 전까지는 추측이다.**
   처음 적었던 설명은 그럴듯했지만 확인하지 않은 것이었고, 실제로는 틀렸다.
2. 프레임워크의 동작이 궁금하면 문서보다 `node_modules`의 소스가 빠를 때가 있다.
   위 분기는 공식 문서에 나오지 않는다.

## 어떻게 확인했나

```bash
pnpm test           # 단위 테스트 통과 확인 (필터링 15개 → 페이지네이션 테스트 3개 추가로 18개)
npx tsc --noEmit     # 타입 오류 없음
pnpm lint            # 린트 오류 없음

# 실제 요청으로 확인 (검증용으로 3001 포트에 별도 서버를 띄움 —
# 이미 3000번에 떠 있던 서버는 손대지 않음)
PORT=3001 pnpm start:dev &

curl "http://localhost:3001/reading-records"                    # 전체 반환
curl "http://localhost:3001/reading-records?status=reading"     # 해당 상태만
curl "http://localhost:3001/reading-records?status=%EB%95%85%EC%BD%A9"  # 400 확인

curl "http://localhost:3001/reading-records?page=2&limit=2"     # 3~4번째 행만, total은 전체 개수
curl -o /dev/null -w "%{http_code}\n" "http://localhost:3001/reading-records?limit=0"   # 400
curl -o /dev/null -w "%{http_code}\n" "http://localhost:3001/reading-records?page=abc"  # 400
```

레코드 두 건(`status: reading`, `status: finished`)을 직접 만들어서 필터가 실제로
건수를 좁히는 것까지 확인한 뒤 삭제했다. 빈 DB에 필터만 걸어보면 항상 `[]`가 나와서
필터가 진짜 동작하는지 증명이 안 된다.

페이지네이션도 같은 이유로 레코드 다섯 건을 만든 뒤 `page=2&limit=2`가 3~4번째 행만
반환하면서 `total`은 여전히 5로 나오는지 확인했다 (`total`이 `data.length`와 같으면
페이지가 실제로 안 잘리고 있다는 뜻이라 구분해서 봐야 한다).

응답 전용 타입은 "타입 검사에 구멍이 있다"는 주장을 실제로 확인한 뒤 테스트를 붙였고,
그 테스트가 정말 잡아내는지도 확인했다 — `toResponse()`에서 `rating`을 일부러 빼고 돌리니
그 테스트를 포함해 5개가 실패했다. 통과만 하는 테스트는 아무것도 지켜주지 않으므로
"실패시켜 보는 것"까지 해야 가드가 완성된다.

## 아직 모르는 것

- 제목 검색(`?q=`)처럼 조건이 더 붙으면 `where`절이 길어지는데, 그때도 지금처럼
  단순히 값을 꽂기만 하면 되는지, 아니면 조립 방식을 바꿔야 하는지
- 정렬 기준이 여러 개(`?sort=status,title`)가 되면 `orderBy`를 배열로 넘겨야 하는데,
  그때 DTO에서 문자열을 어떻게 쪼개고 검증할지
- 응답 전용 타입을 손으로 유지하는 대신 `class-transformer`의 `@Exclude()`와
  `ClassSerializerInterceptor`를 쓰는 방법이 있다고 하는데, 어떤 상황에서 그쪽이 더 나은지
- `data.map()`으로 매 행을 변환하는 비용이 목록이 아주 커졌을 때 문제가 되는지
  (Prisma의 `select`로 아예 필요한 컬럼만 가져오는 방법과 비교해서)
