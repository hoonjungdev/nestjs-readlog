# 05. 데이터베이스 연결 — SQLite + TypeORM, 그리고 마이그레이션

- 날짜: 2026-08-13 ~ 2026-08-14
- 관련 커밋: `b2d5474`, `bf2f0bf`

## 무엇을 만들었나

한 단계에 두 가지를 했다. 순서가 중요했다.

1. **메모리 배열 → SQLite + TypeORM.** 서비스가 `Repository`를 주입받아 실제 DB에 읽고 쓴다.
2. **`synchronize` → 마이그레이션.** 테이블 구조를 TypeORM이 알아서 맞추는 대신, SQL 파일로 남겨 순서대로 실행한다.

1번만 하고 멈추면 "일단 저장은 되는" 상태고, 2번까지 해야 **스키마를 바꿔도 데이터가 안전한** 상태가 된다.

## 왜 필요했나

### 1단계: 서버를 끄면 다 사라진다

지금까지 데이터는 서비스 안의 배열 하나였다.

```ts
private readonly readingRecords: ReadingRecord[] = [];
```

`pnpm start:dev`는 파일을 저장할 때마다 서버를 다시 띄운다. 즉 **코드 한 줄 고칠 때마다 데이터가 초기화**됐다. 독서 기록을 남기는 API인데 기록이 안 남는다.

### 2단계: `synchronize: true`는 개발용 편의 기능이다

DB를 붙인 직후 설정은 이랬다.

```ts
synchronize: true,   // 엔티티를 보고 테이블을 알아서 만들고 바꿈
```

편하다. 엔티티에 컬럼을 추가하면 서버 재시작만으로 테이블에 반영된다. 문제는 **"바꾼다"의 방식을 내가 통제할 수 없다**는 것이다.

컬럼 이름을 `author` → `writer`로 바꾼다고 하자. 사람은 "이름만 바꾸는 것"으로 읽지만, TypeORM이 보는 건 "`author`가 사라지고 `writer`가 생겼다"는 사실뿐이다. 그러면 **컬럼을 지우고 새로 만든다.** 안에 있던 데이터는 같이 사라진다.

게다가 어떤 SQL이 언제 실행됐는지 기록이 남지 않는다. 내 DB와 다른 사람의 DB가 같은 상태라고 보장할 방법이 없다.

그래서 코드에 이런 주석을 달아두고 다음 단계로 미뤄뒀었다.

```ts
// 편리하지만 컬럼을 지우면 데이터도 함께 사라지므로 개발 중에만 쓴다.
// 이후 단계에서 마이그레이션으로 교체하며 끌 예정이다.
```

이번에 그 숙제를 처리했다.

## 핵심 개념 — 내 말로 다시 쓰기

### 1. 엔티티 — 클래스 하나가 테이블 하나

```ts
@Entity('reading_records')
export class ReadingRecord {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;
}
```

3단계에서 DTO에 `@IsString()`을 붙였던 것과 문법이 똑같다. 하는 일도 구조가 같다 — **데코레이터가 클래스에 메타데이터를 붙여두면, 나중에 누군가 그걸 읽어서 동작한다.**

| | 무엇을 설명하나 | 누가 읽나 | 언제 |
| --- | --- | --- | --- |
| DTO + `@IsString()` | API로 **들어오는** 데이터의 규칙 | ValidationPipe | 요청이 올 때 |
| 엔티티 + `@Column()` | DB **테이블**의 구조 | TypeORM | 쿼리 만들 때, 테이블 만들 때 |

기존 `reading-record.interface.ts`는 지웠다. 인터페이스는 타입 검사에만 쓰이고 컴파일하면 사라지는데, 엔티티는 **실행 중에도 살아 있어야** TypeORM이 읽을 수 있기 때문이다. 같은 이름의 타입이 둘일 이유가 없었다.

### 2. Repository — 테이블 하나를 다루는 객체

서비스가 SQL을 직접 쓰지 않는다. `Repository`가 대신 만들어준다.

```ts
constructor(
  @InjectRepository(ReadingRecord)
  private readonly readingRecordsRepository: Repository<ReadingRecord>,
) {}
```

`@InjectRepository(ReadingRecord)`는 "`reading_records` 테이블을 담당하는 Repository를 넣어달라"는 표시다. 2단계에서 컨트롤러가 서비스를 `new` 없이 주입받았던 것과 **완전히 같은 구조**다. 주입받는 대상이 서비스에서 Repository로 바뀐 것뿐이다.

모듈 등록이 두 군데인 게 헷갈렸는데, 역할이 다르다.

| | 어디에 | 하는 일 |
| --- | --- | --- |
| `TypeOrmModule.forRoot({...})` | `AppModule`에 한 번 | **DB 연결 자체**를 만든다 (어떤 DB, 어느 파일) |
| `TypeOrmModule.forFeature([ReadingRecord])` | 각 기능 모듈에 | 이 모듈에서 **어떤 테이블의 Repository를 쓸지** 선언 |

`forRoot`는 집에 수도를 끌어오는 것, `forFeature`는 방마다 수도꼭지를 다는 것에 가깝다.

### 3. `create`와 `save` — 이름이 헷갈린다

```ts
const record = this.readingRecordsRepository.create({ title, author });  // DB 안 감
return this.readingRecordsRepository.save(record);                       // 여기서 INSERT
```

`create`는 **객체만 만든다.** DB에는 아무 일도 일어나지 않는다. 실제 저장은 `save`가 한다.

그리고 `save`는 INSERT와 UPDATE를 **혼자 판단해서** 실행한다.

| 넘긴 객체 | 실행되는 SQL |
| --- | --- |
| `id`가 없음 | `INSERT` |
| `id`가 있음 | `UPDATE` |

그래서 `update()` 메서드에도 `save`를 쓴다. 이미 DB에서 꺼내온 객체라 `id`가 들어 있으니 UPDATE가 된다.

### 4. 전부 `async`가 됐다

DB 작업은 파일/네트워크를 거치므로 결과가 즉시 나오지 않는다. 그래서 모든 메서드가 `Promise`를 반환한다.

```ts
// 이전
findOne(id: number): ReadingRecord { ... }

// 이후
async findOne(id: number): Promise<ReadingRecord> {
  const record = await this.readingRecordsRepository.findOneBy({ id });
  ...
}
```

`await`을 빠뜨리면 값 대신 `Promise` 객체가 그대로 흘러간다. 타입 검사가 대부분 잡아주지만, 테스트 코드에서는 잡히지 않고 통과해버리는 경우가 있었다 (아래 "막혔던 지점" 참고).

컨트롤러는 놀랍게도 거의 안 바꿔도 됐다. **Nest는 컨트롤러가 `Promise`를 반환하면 알아서 기다렸다가 그 결과를 응답 본문으로 쓴다.**

### 5. 마이그레이션 — 스키마 변경을 파일로 남긴다

`migration:generate`가 만들어준 파일은 이게 전부다.

```ts
export class CreateReadingRecords1786716743353 implements MigrationInterface {
  public async up(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`CREATE TABLE "reading_records" (...)`);
  }

  public async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`DROP TABLE "reading_records"`);
  }
}
```

- `up()` — 적용할 때 실행
- `down()` — 되돌릴 때 실행 (`up`을 정확히 취소해야 한다)
- 클래스 이름 뒤 숫자는 **생성 시각(타임스탬프)**. 이게 실행 순서를 정한다.

핵심은 **실행 기록이 DB에 남는다**는 점이다. TypeORM은 `migrations`라는 테이블을 만들어 "어떤 마이그레이션을 실행했는지"를 저장한다. 그래서 `migration:run`을 몇 번 실행해도 이미 돌린 건 건너뛴다.

`synchronize`와 비교하면 이렇다.

| | `synchronize: true` | 마이그레이션 |
| --- | --- | --- |
| 테이블을 누가 맞추나 | TypeORM이 알아서 | 내가 쓴 SQL |
| 실행될 SQL을 미리 볼 수 있나 | ❌ | ✅ 파일에 그대로 있음 |
| 되돌릴 수 있나 | ❌ | ✅ `down()` |
| 실행 이력 | 없음 | `migrations` 테이블 |
| 데이터 손실 위험 | 컬럼 변경 시 있음 | 내가 SQL을 쓰므로 통제 가능 |

### 6. 설정은 한 곳에 — 04단계와 똑같은 교훈

마이그레이션 CLI는 **Nest 앱을 거치지 않고** 직접 DB에 붙는다. 그래서 CLI가 읽을 설정 파일이 따로 필요하다.

여기서 04단계와 판박이인 함정이 보였다. 그때는 이랬다.

> `main.ts`에만 있는 설정은 "실제로 서버를 띄웠을 때만 존재하는 동작"이 된다. 테스트는 그걸 볼 수 없다.

이번엔 이렇게 될 뻔했다.

```text
앱:   app.module.ts 안의 설정   ← 여기만 고치면
CLI:  data-source.ts 안의 설정   ← 여기는 옛날 설정 그대로
```

DB 경로나 엔티티 목록이 두 곳에 따로 적히면, 마이그레이션은 A 파일에 만들고 앱은 B 파일을 읽는 사고가 난다. 그래서 **설정은 `data-source.ts` 하나에만 쓰고 `AppModule`이 가져다 쓰게** 했다.

```ts
// data-source.ts
export const dataSourceOptions: DataSourceOptions = { ... };
export default new DataSource(dataSourceOptions);   // CLI는 default export를 찾는다

// app.module.ts
TypeOrmModule.forRoot({
  ...dataSourceOptions,
  migrationsRun: true,
}),
```

`migrationsRun: true`는 **앱이 켜질 때 밀린 마이그레이션을 자동 실행**한다. 덕분에 e2e 테스트의 인메모리 DB도 앱이 뜨는 순간 테이블을 갖게 된다. 운영에서는 배포 과정에서 따로 실행하는 편이 안전하다고 한다 (앱 인스턴스가 여러 개면 동시에 실행될 수 있어서).

## 이번 단계에 쓴 문법 — 빠른 참조

### 엔티티 데코레이터

| 문법 | 하는 일 | 예시 |
| --- | --- | --- |
| `@Entity('테이블명')` | 이 클래스가 곧 테이블 | `@Entity('reading_records')` |
| `@PrimaryGeneratedColumn()` | 기본 키 + 값 자동 생성 | `id: number` |
| `@Column()` | 일반 컬럼 | `title: string` |

### Repository

| 문법 | 하는 일 |
| --- | --- |
| `repo.create({...})` | 엔티티 객체만 생성 (DB 안 감) |
| `repo.save(entity)` | id 없으면 INSERT, 있으면 UPDATE |
| `repo.find()` | 전체 조회 |
| `repo.findOneBy({ id })` | 조건 조회, **없으면 `null`** (예외 아님) |
| `repo.remove(entity)` | 엔티티를 넘겨서 삭제 |

### 마이그레이션 명령

| 명령 | 하는 일 |
| --- | --- |
| `pnpm migration:generate src/migrations/이름` | 엔티티와 **현재 DB의 차이**를 SQL 파일로 |
| `pnpm migration:run` | 밀린 마이그레이션 실행 |
| `pnpm migration:revert` | 마지막 것의 `down()` 실행 |
| `pnpm migration:show` | `[X]` 실행됨 / `[ ]` 대기중 목록 |

### 비동기 테스트

| 문법 | 하는 일 |
| --- | --- |
| `await expect(p).rejects.toThrow(X)` | Promise가 X로 **거부되는지** 검사 |
| `expect(() => f()).toThrow(X)` | 동기 함수가 던지는지 검사 (비동기엔 못 씀) |

## 막혔던 지점 ⭐

### 1. `save`가 오염된 반환값을 숨겨준다

3단계에서 잡았던 `Object.assign` 버그가 **DB를 붙이니 더 교묘해졌다.**

`ValidationPipe`를 거친 DTO는 안 보낸 필드도 `undefined` 값으로 갖고 있다. 그래서 `Object.assign(record, dto)`를 쓰면 기존 값이 `undefined`로 덮인다. 여기까지는 3단계에서 안 내용이다.

그런데 DB를 붙인 뒤에 그 코드를 되돌려보면, **DB에는 아무 문제가 없다.** `save()`가 `undefined`인 속성은 UPDATE문에서 아예 제외하기 때문이다.

```text
객체:  { id: 1, title: undefined, author: 'Robert C. Martin' }
SQL:   UPDATE reading_records SET author = ? WHERE id = 1     ← title은 안 건드림
```

DB만 확인하는 테스트는 통과한다. 그런데 **API 응답은 그 오염된 객체 그대로 나간다.** `title`이 사라진 응답이 클라이언트에게 간다.

그래서 `update` 테스트를 두 겹으로 만들었다.

```ts
// 1. 반환값 — 이게 그대로 응답이 된다
expect(returnedRecord.title).toBe('클린 코드');

// 2. DB에 실제로 저장된 값 — 다시 꺼내와서 확인
const reloadedRecord = await service.findOne(createdRecord.id);
expect(reloadedRecord.title).toBe('클린 코드');
```

배운 것: **"DB에 잘 저장됐다"와 "클라이언트가 받는 값이 맞다"는 서로 다른 주장이다.** 하나만 검사하면 다른 하나가 뚫린다.

### 2. 동기에서 비동기로 바꾸면 테스트 문법도 바뀐다

```ts
// 이전 — 동기
expect(() => service.findOne(999)).toThrow(NotFoundException);

// 이후 — 비동기
await expect(service.findOne(999)).rejects.toThrow(NotFoundException);
```

`async` 함수는 예외를 **던지는(throw)** 게 아니라 Promise를 **거부(reject)** 한다. 그래서 `toThrow`로는 못 잡는다. `rejects`를 붙여야 하고, 앞에 `await`도 필요하다.

무서운 건 이걸 빼먹어도 **테스트가 실패하지 않고 통과한다**는 점이다. `expect(() => ...)` 안의 함수는 Promise를 반환하고 끝나며, 예외는 그 바깥에서 조용히 떠돌게 된다.

### 3. 테스트가 끝났는데 프로세스가 안 죽는다

단위 테스트에서 DB 연결을 열면 닫아줘야 한다.

```ts
afterEach(async () => {
  await module.close();
});
```

안 닫으면 jest가 "테스트는 끝났는데 뭔가 아직 살아 있다"며 프로세스를 놓지 않는다.

### 4. TypeORM 1.x에는 `sqlite` 드라이버가 없다

`type: 'sqlite'`를 쓰려 했으나 1.x에서는 지원되지 않아 `better-sqlite3`를 썼다. 버전도 peer 범위에 맞춰 12.x로 고정했다. **문서 예제가 대부분 0.3.x 기준**이라 그대로 따라 하면 어긋나는 지점이 있다.

### 5. `migration:generate`가 아무것도 안 만든다

가장 헷갈린 부분. `generate`는 엔티티 정의를 보고 SQL을 만드는 게 아니라, **엔티티 정의와 "지금 연결된 DB의 실제 상태"를 비교해서 그 차이를 만든다.**

이미 `synchronize: true`가 `reading_records` 테이블을 만들어 둔 상태였으니, 비교 결과는 "차이 없음"이었다. 초기 `CREATE TABLE`을 얻으려면 **빈 DB를 기준으로** 생성해야 했다.

```bash
DATABASE_PATH=/tmp/gen.sqlite pnpm migration:generate src/migrations/CreateReadingRecords
```

### 6. 기존 DB에 마이그레이션을 돌리면 "이미 있다"고 실패한다

위에서 만든 마이그레이션을 기존 개발 DB(`readlog.sqlite`)에 실행하니 이렇게 됐다.

```text
QueryFailedError: table "reading_records" already exists
  at CreateReadingRecords1786716743353.up (...)
  code: 'SQLITE_ERROR'
```

당연했다. 그 DB에는 `synchronize`가 만든 테이블이 이미 있는데, **`migrations` 테이블에는 "실행했다"는 기록이 없다.** TypeORM 입장에서는 아직 한 번도 실행 안 된 마이그레이션이니 처음부터 만들려 한다.

여기서 알게 된 것: **마이그레이션은 "현재 스키마"가 아니라 "실행 이력"으로 상태를 판단한다.** 둘이 어긋나면 이런 사고가 난다.

개발용 DB의 데이터는 테스트로 넣은 1건뿐이고 `.gitignore`에도 걸려 있어서, 파일을 지우고 마이그레이션으로 처음부터 다시 만드는 쪽을 택했다. (실제 데이터가 있었다면 이 선택은 불가능하다. 그럴 땐 이미 실행된 것으로 기록만 남기는 방법을 찾아야 한다.)

### 7. 파일 경로 패턴(glob)은 "빌드했을 때만" 동작한다

TypeORM 예제는 마이그레이션 목록을 보통 이렇게 쓴다.

```ts
migrations: ['dist/migrations/*.js'],   // 파일 경로 패턴(glob)
```

처음엔 "e2e는 ts-jest가 메모리에서 돌리니 `dist`를 못 볼 것"이라고 짐작했다. **틀렸다.** 실제로 바꿔서 돌려보니 13개가 그대로 통과했다. 경로가 실행 위치(프로젝트 루트) 기준으로 풀리고, 마침 `pnpm build`를 해둔 상태라 `dist/migrations/`에 파일이 있었기 때문이다.

진짜 문제는 다른 데 있었다. `dist`를 지우고 다시 돌려봤다.

```text
Tests: 9 failed, 4 passed, 13 total
```

즉 **테스트 통과 여부가 "빌드를 했는지"에 달려 있다.** `dist`는 `.gitignore`에 있으니, 저장소를 새로 받은 사람은 빌드 없이 테스트를 돌리는 순간 테이블 없는 DB를 만나게 된다. 원인도 안 보인다 — "마이그레이션을 못 찾았다"는 에러가 아니라 그냥 요청이 실패한다.

그래서 클래스를 직접 import해서 배열에 넣었다.

```ts
migrations: [CreateReadingRecords1786716743353],
```

새 마이그레이션마다 손으로 추가해야 하지만, 대신 **빌드 여부와 무관하게 똑같이 동작하고 목록이 눈에 보인다.** 04단계의 "설정이 환경마다 갈라지면 안 된다"와 같은 판단이다.

여기서 다시 확인한 것: **짐작한 원인과 실제 원인이 달라도 결론은 같을 수 있다.** 그래도 확인은 해야 한다. 안 그러면 노트에 틀린 설명이 남는다.

## 어떻게 확인했나

```bash
# 1. 마이그레이션 생성 — 빈 DB 기준
DATABASE_PATH=/tmp/gen.sqlite pnpm migration:generate src/migrations/CreateReadingRecords
# Migration ...-CreateReadingRecords.ts has been generated successfully.

# 2. 기존 DB 사본에 실행 — 실패를 확인
cp readlog.sqlite /tmp/devcopy.sqlite
DATABASE_PATH=/tmp/devcopy.sqlite pnpm migration:run
# QueryFailedError: table "reading_records" already exists

# 3. 개발 DB를 지우고 마이그레이션으로 다시 생성
rm readlog.sqlite
pnpm start:dev
pnpm migration:show        # [X] CreateReadingRecords...

# 4. 마이그레이션 목록을 glob으로 바꿔보고 비교
#    (dist가 있을 때) 13 passed  → (dist를 지우면) 9 failed, 4 passed

# 5. 전체 검증
pnpm lint
pnpm build                 # 타입 검사
pnpm test                  # 10 passed
pnpm test:e2e              # 13 passed
```

e2e 13개가 통과한 게 이번 단계의 진짜 증거다. **`synchronize`를 껐으니, 마이그레이션이 실제로 테이블을 만들지 못했다면 전부 실패했을 것이다.**

API 계약을 하나도 안 바꿨기 때문에 e2e 테스트는 **한 줄도 수정하지 않았다.** 저장소를 배열에서 SQLite로 통째로 갈아치웠는데 테스트가 그대로 통과한다는 것 자체가, e2e 테스트가 "구현"이 아니라 "겉으로 드러나는 약속"을 검사하고 있다는 뜻이다.

## 아직 모르는 것

- **단위 테스트는 아직 `synchronize: true`를 쓴다.** (`reading-records.service.spec.ts`가 자체 `TypeOrmModule.forRoot`를 갖고 있음) 즉 엔티티와 마이그레이션이 어긋나도 단위 테스트는 통과한다. 04단계에서 배운 "환경이 갈라지면 안 된다"가 여기 그대로 남아 있는 셈. 다음에 정리해야 한다.
- 마이그레이션 클래스를 배열에 손으로 등록하는 방식이 10개, 20개가 되면 어떻게 되나?
- 운영 배포에서는 `ts-node` 없이 마이그레이션을 어떻게 실행하나? (`dist`로 빌드된 `.js`를 써야 할 텐데)
- **이미 데이터가 있는 테이블에 `NOT NULL` 컬럼을 추가하면** 기존 행은 어떤 값을 갖나? 기본값을 반드시 줘야 하나?
- 04단계에서 남긴 질문이 아직 그대로다 — 응답에서 `undefined`와 `null`을 어떻게 구분해 설계할까. `nullable: true` 컬럼을 만들면 이게 바로 문제가 된다.
- SQLite는 컬럼 변경(ALTER)을 제대로 지원하지 않아 TypeORM이 "새 테이블 만들고 → 복사하고 → 바꿔치기" 하는 식으로 SQL을 만든다던데, 실제로 컬럼을 바꿔볼 때 확인해봐야 한다.
