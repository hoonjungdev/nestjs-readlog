# 03. 입력 검증 (ValidationPipe)

- 날짜: 2026-08-11
- 관련 커밋: `4e82ad9`

## 무엇을 만들었나

`class-validator` / `class-transformer`를 도입하고 `ValidationPipe`를 전역 등록해서,
잘못된 요청이 서비스에 도달하기 전에 400으로 막히도록 했다.

## 왜 필요했나

검증을 붙이기 전에 **실제로 무엇이 뚫리는지** 직접 확인했다.

```bash
curl -X POST localhost:3000/reading-records \
  -H 'Content-Type: application/json' -d '{"title": 12345}'
# → 201 {"id":1,"title":12345}      제목이 숫자, 저자는 아예 없음

curl -X POST localhost:3000/reading-records \
  -H 'Content-Type: application/json' -d '{}'
# → 201 {"id":2}                    빈 기록이 생성됨
```

`CreateReadingRecordDto`에 `title: string`이라고 분명히 적어놨는데도 전부 통과했다.

## 핵심 개념 — 내 말로 다시 쓰기

### 1. 타입은 런타임에 사라진다

이게 이번 단계의 뿌리다. 컴파일된 결과를 직접 열어봤다.

```bash
cat dist/reading-records/dto/create-reading-record.dto.js
```

원본:

```ts
class CreateReadingRecordDto {
  title: string;
  author: string;
}
```

컴파일 후:

```js
class CreateReadingRecordDto {
    title;      // ← : string 이 흔적도 없이 사라짐
    author;
}
```

**TypeScript는 내가 코드를 쓸 때 도와주는 도구지, 낯선 사람이 이상한 요청을 보낼 때 막아주는 도구가 아니다.**
서버가 실행 중일 때는 `title`이 문자열이어야 한다는 사실을 알 방법이 없다.

| | 언제 동작하나 | 무엇을 막나 |
| --- | --- | --- |
| 타입 (`title: string`) | 컴파일 시점 | 내가 코드에서 저지르는 실수 |
| 검증 (`@IsString()`) | 런타임 | 외부에서 들어오는 잘못된 데이터 |

**둘 다 필요하다.** 하나로 다른 하나를 대신할 수 없다.

### 2. 그런데 데코레이터는 살아남는다

`@IsString()`을 붙이고 다시 컴파일해보면:

```js
class UpdateReadingRecordDto {
    title;
    author;
}
__decorate([                                    // ← 이게 남는다
    (0, class_validator_1.IsOptional)(),
    (0, class_validator_1.IsString)(),
    (0, class_validator_1.IsNotEmpty)(),
    __metadata("design:type", String)
], UpdateReadingRecordDto.prototype, "title", void 0);
```

타입은 사라졌지만 데코레이터가 붙인 **메타데이터는 JS 코드로 남았다.**
`ValidationPipe`는 실행 중에 이 정보를 읽어서 검증한다.
이것이 "타입 대신 데코레이터를 쓰는" 이유다.

### 3. 세 조각이 어떻게 맞물리나

| 조각 | 역할 |
| --- | --- |
| `class-validator` | `@IsString()` 같은 규칙을 메타데이터로 붙임 |
| `class-transformer` | 들어온 평범한 JSON 객체를 **DTO 클래스 인스턴스로 변환** |
| `ValidationPipe` | 위 둘을 조합해 "변환 → 검증 → 실패 시 400"을 자동 수행 |

2번이 왜 필요한가? 검증 규칙은 **클래스에** 붙어 있는데,
요청으로 들어온 건 그냥 `{title: "..."}`인 평범한 객체라 그 클래스와 아무 관련이 없기 때문이다.
(→ 이 변환이 나중에 버그를 일으킨다. "막혔던 지점" 참고)

### 4. 전역 파이프의 영향 범위

```ts
// src/main.ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
  }),
);
```

`useGlobalPipes`는 **앱 전체**에 적용된다. 지금 있는 라우트뿐 아니라
앞으로 추가할 모든 컨트롤러의 `@Body()`, `@Query()`, `@Param()`에 자동으로 걸린다.
편하지만 그만큼 영향 범위가 넓다 — 특정 라우트만 예외로 두려면 그 라우트에 개별 파이프를 지정해야 한다.

| 옵션 | 하는 일 |
| --- | --- |
| `whitelist: true` | DTO에 **검증 데코레이터가 붙은 속성만** 남기고 나머지는 조용히 삭제 |
| `forbidNonWhitelisted: true` | 삭제하는 대신 **400으로 거부**하고 어떤 필드가 문제인지 알려줌 |

`forbidNonWhitelisted`는 `whitelist: true`가 켜져 있어야 동작한다.
오타를 낸 클라이언트가 "왜 내 값이 무시되지?" 하고 헤매는 것보다
명확히 에러를 받는 게 낫기 때문에 둘 다 켰다.

### 5. `?`와 `@IsOptional()`은 다른 층에서 일한다

```ts
export class UpdateReadingRecordDto {
  @IsOptional()      // 런타임: 값이 없으면 나머지 검증을 건너뜀
  @IsString()
  @IsNotEmpty()
  title?: string;    // 컴파일 시점: string | undefined 로 취급
}
```

- `?`만 있으면 → 실행 중에 아무 보호가 없다
- `@IsOptional()`만 있으면 → 타입스크립트가 "이 값은 항상 있다"고 착각한다

**둘 다 써야 반쪽이 아니다.**

## 이번 단계에 쓴 문법 — 빠른 참조

### 검증 데코레이터 (`class-validator`)

이번에 실제로 쓴 것:

| 문법 | 하는 일 | 통과 | 거부 |
| --- | --- | --- | --- |
| `@IsString()` | 값이 **문자열**인지 검사 | `"클린 코드"` | `12345`, `true` |
| `@IsNotEmpty()` | 값이 **비어 있지 않은지** 검사 | `"책"` | `""`, `null`, `undefined` |
| `@IsOptional()` | 값이 `undefined`/`null`이면 **나머지 검증을 건너뜀** | 필드를 아예 안 보냄 | (거부하지 않음) |

여러 개를 겹쳐 쓸 수 있다.

```ts
@IsOptional()    // 안 보냈으면 나머지를 건너뛰고 통과
@IsString()      // 문자열인지
@IsNotEmpty()    // 비어 있지 않은지
title?: string;
```

**주의: 먼저 걸리는 규칙에서 멈추지 않는다.** 붙어 있는 규칙이 전부 적용되고,
실패한 것이 **모두** 보고된다. `@IsOptional()`만 예외적으로 "값이 없으면 나머지를 건너뛰는" 역할이다.

그래서 `undefined`를 보내면 에러가 두 개 나온다.

```json
{"message":["author should not be empty","author must be a string"]}
```

처음엔 "필드 하나인데 왜 메시지가 두 개지?" 싶었는데, 규칙 두 개가 각각 실패한 것이었다.

`@IsString()`과 `@IsNotEmpty()`를 **둘 다** 쓰는 이유 (직접 확인함):

| 붙인 것 | `""` | `12345` |
| --- | --- | --- |
| `@IsString()`만 | ✅ 통과해버림 | ❌ 거부 |
| `@IsNotEmpty()`만 | ❌ 거부 | ✅ 통과해버림 |
| **둘 다** | ❌ 거부 | ❌ 거부 |

하나만 쓰면 반드시 구멍이 생긴다.

앞으로 쓸 일이 생길 만한 것 (아직 안 씀):

| 문법 | 하는 일 |
| --- | --- |
| `@IsInt()` / `@IsNumber()` | 정수 / 숫자인지 |
| `@Min(1)` / `@Max(5)` | 숫자 범위 (평점 같은 데 쓸 듯) |
| `@MaxLength(200)` | 문자열 길이 제한 |
| `@IsDateString()` | 날짜 형식 문자열인지 (읽기 시작일 등) |
| `@IsEnum(...)` | 정해진 값 중 하나인지 (독서 상태 등) |

### 파이프 설정

| 문법 | 하는 일 |
| --- | --- |
| `app.useGlobalPipes(pipe)` | 앱 **전체**의 모든 라우트에 파이프 적용 |
| `whitelist: true` | DTO에 검증 데코레이터가 붙은 속성만 남기고 나머지는 삭제 |
| `forbidNonWhitelisted: true` | 삭제 대신 **400으로 거부**. `whitelist`가 켜져 있어야 동작 |

### 패키지

| 패키지 | 역할 |
| --- | --- |
| `class-validator` | `@IsString()` 같은 검증 규칙 제공 |
| `class-transformer` | 평범한 JSON 객체를 DTO 클래스 인스턴스로 변환 |

```bash
pnpm add class-validator class-transformer
```

두 개를 같이 설치해야 한다. `ValidationPipe`가 내부에서 둘 다 쓰기 때문이다.

## 막혔던 지점 ⭐

### 증상

`ValidationPipe`를 붙인 뒤 PATCH를 테스트했더니:

```bash
curl -X PATCH localhost:3000/reading-records/1 \
  -H 'Content-Type: application/json' -d '{"author":"Robert C. Martin"}'
# → {"id":1,"author":"Robert C. Martin"}      title이 사라졌다!

curl -X PATCH localhost:3000/reading-records/1 \
  -H 'Content-Type: application/json' -d '{}'
# → {"id":1}                                  전부 사라졌다!
```

**검증을 붙이기 전에는 정상이었다.** 검증을 추가했더니 멀쩡하던 기능이 깨졌다.

### 원인 추적

문제의 코드는 2단계에서 쓴 이것이었다.

```ts
Object.assign(readingRecord, updateReadingRecordDto);
```

컴파일된 DTO를 열어보니 힌트가 있었다.

```js
class UpdateReadingRecordDto {
    title;      // 초기값 없는 클래스 필드
    author;
}
```

이게 무슨 의미인지 직접 실험해봤다.

```bash
node -e '
class UpdateDto { title; author; }
const dto = new UpdateDto();
console.log("실제로 가진 키:", Object.keys(dto));
const record = { id: 1, title: "클린 코드", author: "로버트 C. 마틴" };
Object.assign(record, dto);
console.log("Object.assign 후:", record);
'
```

```text
실제로 가진 키: [ 'title', 'author' ]
Object.assign 후: { id: 1, title: undefined, author: undefined }
```

범인을 잡았다. **초기값 없이 선언된 클래스 필드도 인스턴스에 `undefined` 값으로 실제로 만들어진다.**
(`tsconfig.json`의 `target`이 ES2023이라 `useDefineForClassFields`가 켜진 결과다.)

### 전체 인과관계

| | `@Body()`가 주는 것 | `Object.assign` 결과 |
| --- | --- | --- |
| **검증 붙이기 전** | JSON을 파싱한 날것의 객체. `{author: "..."}` — 키가 하나뿐 | `author`만 복사됨 ✓ |
| **검증 붙인 후** | `class-transformer`가 만든 **DTO 인스턴스**. `title`, `author` 키가 항상 존재하고 안 보낸 건 `undefined` | `title: undefined`를 기존 값 위에 덮어씀 💥 |

### 배운 것

**새 도구는 새 버그를 데려온다.**
`ValidationPipe`를 붙이자 `@Body()`가 주는 값의 **성질 자체가 바뀌었고**,
그 위에서 돌던 `Object.assign`이 조용히 데이터를 지웠다.

라이브러리를 추가할 때는 "무엇이 좋아지나"뿐 아니라
**"기존 코드에 들어오는 값의 모양이 바뀌지 않나"** 를 함께 봐야 한다.

### 수정

`Object.assign`은 값이 `undefined`인지 따지지 않고 무조건 복사한다.
그래서 **실제로 보낸 필드만 골라서** 반영하도록 바꿨다.

```ts
if (updateReadingRecordDto.title !== undefined) {
  readingRecord.title = updateReadingRecordDto.title;
}
if (updateReadingRecordDto.author !== undefined) {
  readingRecord.author = updateReadingRecordDto.author;
}
```

필드가 늘어나면 반복이 길어지지만, 지금은 **읽어서 바로 이해되는 게 더 중요**하다고 판단했다.

### 왜 기존 단위 테스트는 이 버그를 못 잡았나

테스트가 이렇게 되어 있었다.

```ts
service.update(createdRecord.id, { author: 'Robert C. Martin' });
//                                ^^^ 평범한 객체 리터럴 — author 키만 있음
```

**단위 테스트는 파이프를 거치지 않는다.** 그래서 실제 상황과 다른 모양의 값을 넘기고 있었다.
실제 파이프가 만들어내는 것과 똑같이 고쳤다.

```ts
const updateDto = new UpdateReadingRecordDto();
updateDto.author = 'Robert C. Martin';    // title은 undefined인 채로 남음
service.update(createdRecord.id, updateDto);
```

그리고 이 테스트가 **정말로 버그를 잡는지** 확인하려고, 일부러 옛날 코드로 되돌려 실행해봤다.

```text
● update › updates only the given fields and keeps the rest unchanged
  Expected: "클린 코드"
  Received: undefined
```

의도한 대로 실패했다. **회귀 테스트는 반드시 "실패하는 것"까지 확인해야 의미가 있다.**
통과하는 것만 보면, 사실은 아무것도 검사하지 않는 테스트일 수도 있다.

## 예상치 못한 발견: e2e 테스트가 검증을 안 거친다

`test/app.e2e-spec.ts`에 이미 e2e 테스트가 6개 있었고 전부 통과했다.
그런데 테스트가 앱을 만드는 방식을 보니 이상했다.

```ts
app = moduleFixture.createNestApplication();
await app.init();
```

`ValidationPipe`는 `main.ts`의 `bootstrap()` 안에서 등록되는데,
e2e 테스트는 `main.ts`를 실행하지 않는다. 그럼 검증이 안 도는 것 아닌가?

임시 테스트를 만들어 확인했다.

```text
>>> POST 응답 상태: 201
>>> POST 응답 본문: {"id":1,"title":"제목만"}
```

`author` 없이 POST했는데 **400이 아니라 201**이 나왔다. 가설이 맞았다.

**현재 e2e 테스트는 `ValidationPipe`를 전혀 거치지 않는다.**
"테스트가 통과한다"가 "실제 서버에서도 그렇게 동작한다"를 의미하지 않는 경우다.
전역 설정을 `main.ts`에만 두면 테스트 환경과 실제 환경이 갈라진다.

→ 아직 고치지 않았다. 다음 단계 과제.
