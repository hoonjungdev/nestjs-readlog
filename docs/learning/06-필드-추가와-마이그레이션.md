# 06. 필드 추가 — 두 번째 마이그레이션과 undefined/null

- 날짜: 2026-08-15
- 관련 커밋: `e3520cf`

## 무엇을 만들었나

독서 기록에 필드 두 개를 추가했다. 성격이 정반대인 것으로 골랐다.

| | `status` | `rating` |
| --- | --- | --- |
| 값 | 정해진 3개 중 하나 | 1~5 정수 |
| 비어도 되나 | ❌ NOT NULL | ✅ nullable |
| 기본값 | `want_to_read` | 없음 |

곁들여 5단계에서 미뤄둔 숙제도 처리했다. 단위 테스트가 아직 `synchronize: true`로 자기만의 테이블을 만들던 것을 마이그레이션을 쓰도록 바꿨다.

## 왜 필요했나

지금까지 독서 기록에는 `title`과 `author`밖에 없었다. **"읽었다"는 사실 자체가 안 들어 있었다.** 독서 기록 API인데 책 목록이었다.

그리고 5단계 노트의 "아직 모르는 것"에 남아 있던 질문들이 전부 "컬럼을 하나 더 추가해보면" 답이 나오는 것들이었다.

## 핵심 개념 — 내 말로 다시 쓰기

### 1. 정해진 값 3개를 타입으로 쓰는 두 가지 방법

TypeScript에는 방법이 둘 있다.

```ts
// 방법 1 — 유니온 타입
type ReadingStatus = 'want_to_read' | 'reading' | 'finished';

// 방법 2 — enum
enum ReadingStatus {
  WantToRead = 'want_to_read',
  Reading = 'reading',
  Finished = 'finished',
}
```

유니온 쪽이 훨씬 짧다. 그런데 이 프로젝트에서는 enum을 골랐다. 이유는 3단계에서 배운 그것이다.

> **타입은 컴파일하면 사라진다. 런타임 검증은 별개다.**

DTO에 붙일 `@IsEnum(ReadingStatus)`는 **서버가 돌아가는 중에** 실행되는 함수 호출이다. 그때 값 목록이 실제로 존재해야 한다.

| | 컴파일 후 | `@IsEnum()`에 넘길 수 있나 |
| --- | --- | --- |
| `type` (유니온) | 사라짐 | ❌ |
| `enum` | 객체로 남음 | ✅ |

유니온을 쓰려면 검증용 배열을 따로 또 써야 한다.

```ts
type ReadingStatus = 'want_to_read' | 'reading' | 'finished';  // 타입용
const STATUSES = ['want_to_read', 'reading', 'finished'];       // 런타임용 — 같은 걸 두 번
```

**값이 두 곳에 흩어진다.** 4단계(`main.ts` vs `AppModule`)와 5단계(`app.module.ts` vs `data-source.ts`)에서 계속 부딪힌 그 문제와 같은 모양이다. 이 프로젝트에서 세 번째로 나온 셈이다.

### 2. `undefined`와 `null`은 다른 말이다

4단계부터 두 번 미뤄왔던 질문인데, nullable 컬럼을 만들자마자 실체가 생겼다.

별점을 **지우고 싶을 때** 어떻게 요청하나?

```
PATCH { "rating": 3 }      → 3점으로 바꿔라
PATCH { }                  → 별점은 건드리지 마라    (필드 없음  = undefined)
PATCH { "rating": null }   → 별점을 지워라           (명시적으로 비움 = null)
```

셋이 서로 다른 뜻이다. `undefined`는 **"관심 없음"**, `null`은 **"비워라"**.

그래서 서비스에서 `??`가 아니라 `!== undefined`를 쓴다.

```ts
// ❌ null까지 걸러내므로 "지워라"가 무시된다
readingRecord.rating = dto.rating ?? readingRecord.rating;

// ✅ undefined만 걸러낸다
if (dto.rating !== undefined) {
  readingRecord.rating = dto.rating;
}
```

`@IsOptional()`이 이걸 가능하게 해준다. 이 데코레이터는 값이 **undefined 또는 null이면 나머지 검증을 건너뛴다.** 그래서 `null`이 `@IsInt()`에 걸리지 않고 서비스까지 도착한다.

### 3. nullable은 두 곳에 따로 말해야 한다

```ts
@Column({ type: 'integer', nullable: true })   // DB에게: NOT NULL 걸지 마라
rating: number | null;                          // TypeScript에게: 읽을 때 null일 수 있다
```

하나만 쓰면 어긋난다.

| 빠뜨린 것 | 생기는 일 |
| --- | --- |
| `nullable: true` 없음 | DB가 NOT NULL을 걸어 INSERT 실패 |
| `\| null` 없음 | 타입은 `number`라고 믿는데 실제로 null이 들어와 런타임에 터짐 |

`tsconfig.json`의 `strictNullChecks: true`가 켜져 있어서, `| null`을 쓰면 컴파일러가 null 확인을 강제해준다.

## 이번 단계에 쓴 문법 — 빠른 참조

### 검증 데코레이터

| 문법 | 하는 일 | 예시 |
| --- | --- | --- |
| `@IsEnum(E)` | 값이 enum `E`의 값 목록에 있는지 | `@IsEnum(ReadingStatus)` |
| `@IsInt()` | 정수인지 (3.5도 `'5'`도 거부) | `@IsInt() rating?: number` |
| `@Min(n)` / `@Max(n)` | 숫자 범위 | `@Min(1) @Max(5)` |

### 엔티티 컬럼 옵션

| 문법 | 하는 일 |
| --- | --- |
| `type: 'simple-enum', enum: E` | SQLite에는 enum이 없어서 **varchar + CHECK 제약**으로 만들어진다 |
| `nullable: true` | DB에 NOT NULL 제약을 걸지 않는다 |
| `default: 값` | **TypeORM이** INSERT할 때 채워 넣는 값 (아래 "막혔던 지점" 2번 참고) |

## 막혔던 지점 ⭐

### 1. 서버가 3개 떠 있어서 마이그레이션이 두 번 실행됐다

이번 단계 최대의 사고. 마이그레이션을 만들고 실행하려는데, `migration:run`을 치기도 전에 이미 실행돼 있었다.

```text
$ pnpm migration:show
[X] 1 CreateReadingRecords1786716743353
[X] 3 AddStatusAndRating1786800197352     ← 아직 실행 안 했는데 [X]?

$ pnpm migration:run
No migrations are pending
```

DB의 이력 테이블을 열어보니 더 이상했다.

```text
id: 1, name: 'CreateReadingRecords1786716743353'
id: 2, name: 'AddStatusAndRating1786800197352'
id: 3, name: 'AddStatusAndRating1786800197352'    ← 같은 게 두 번
```

`ps aux`로 찾아낸 원인:

```text
PID 67002  nest start --watch    ← 화요일 밤부터 살아 있음
PID 65297  nest start --watch    ← 또 하나
PID 51363  node dist/main
```

`AppModule`에 `migrationsRun: true`가 있었다. **`data-source.ts`를 저장하는 순간 watch 서버 두 개가 각각 재시작하면서, 각자 마이그레이션을 한 번씩 실행한 것이다.**

5단계 노트에 이렇게 적어뒀었다.

> 운영에서는 배포 과정에서 따로 실행하는 편이 안전하다고 한다 **(앱 인스턴스가 여러 개면 동시에 실행될 수 있어서).**

들은 얘기로 적어둔 위험을 **로컬에서 그대로 재현했다.** 노트에 적어둔 게 실제로 일어날 때까지 걸린 시간: 하루.

#### 이게 왜 위험한가 — 사본으로 확인

이번 마이그레이션의 `up()`은 "새 테이블 만들고 복사"인데, 복사하는 줄이 이렇다.

```sql
INSERT INTO "temporary_reading_records"("id","title","author") SELECT ... FROM "reading_records"
```

**`status`와 `rating`을 복사하지 않는다.** 두 번째로 실행되면 어떻게 되는지 백업 사본으로 돌려봤다.

```text
실험 전:  status: 'finished',      rating: 5      ← 다 읽고 별점 5점 준 기록
실험 후:  status: 'want_to_read',  rating: null   ← "읽고 싶은 책"으로 되돌아감
```

**에러도 경고도 없이 데이터가 사라진다.** 이번엔 실제 데이터가 마침 `want_to_read` / `null`이라 결과가 같아서 티가 안 났을 뿐이다.

#### 배운 것

**마이그레이션은 "한 번만 실행된다"를 스스로 보장하지 못한다.** TypeORM은 이력 테이블을 확인하고 실행하는데, 두 프로세스가 거의 동시에 확인하면 둘 다 "아직 안 돌았네"라고 판단한다. 5단계에서 배운 "실행 이력으로 상태를 판단한다"의 빈틈이다.

그래서 `migrationsRun`을 메모리 DB일 때만 켜도록 바꿨다.

```ts
// data-source.ts
export const isInMemoryDatabase = databasePath === ':memory:';

// app.module.ts
migrationsRun: isInMemoryDatabase,
```

메모리 DB(테스트)는 앱이 뜰 때마다 빈 DB를 새로 받으므로 자동 실행이 없으면 테이블 자체가 없다. 반면 파일 DB(개발/운영)는 `pnpm migration:run`으로 **사람이 한 번만** 실행한다.

### 2. DB의 `DEFAULT`는 사실 거의 쓰이지 않는다

가장 예상을 벗어난 발견.

마이그레이션이 만든 스키마에는 분명 `DEFAULT`가 있다.

```sql
"status" varchar CHECK( ... ) NOT NULL DEFAULT ('want_to_read')
```

그래서 "엔티티에는 `default`를 안 써도 DB가 채워주겠지"라고 생각했다. **틀렸다.** 엔티티에서 `default`를 빼고 저장해봤더니 이렇게 됐다.

```text
QueryFailedError: NOT NULL constraint failed: reading_records.status
query: INSERT INTO "reading_records"("id","title","author","status","rating")
       VALUES (NULL, ?, ?, NULL, NULL)
                          ↑ status에 NULL을 "명시"했다
```

**DB의 `DEFAULT`는 컬럼을 INSERT문에서 생략했을 때만 적용된다.** 엔티티에 `default`가 없으니 TypeORM이 `NULL`을 명시적으로 써넣었고, 그 순간 DEFAULT는 무력화되고 NOT NULL 제약에 걸렸다.

정리하면 이렇다.

| | 실제로 일하는 곳 |
| --- | --- |
| 엔티티의 `default` | **앱이 INSERT할 때** — TypeORM이 이 값을 넣는다 |
| DB 스키마의 `DEFAULT` | **마이그레이션이 기존 행을 채울 때**, 그리고 TypeORM을 거치지 않는 직접 SQL |

둘이 같은 값을 가리키지만 일하는 순간이 다르다. 마이그레이션이 둘 다 만들어주니 평소엔 신경 쓸 일이 없는데, **엔티티에서 `default`를 지우면 조용히 깨진다.**

#### 곁가지 확인 — `status: undefined`를 명시하면?

서비스에서 이렇게 쓰려니 걱정됐다.

```ts
status: createReadingRecordDto.status,   // 안 보냈으면 undefined인데?
```

`undefined`가 명시적으로 들어가서 위 사고가 나는 것 아닌가? 찍어봤다.

```text
save() 호출 전 객체: {"title":"클린 코드","author":"로버트 C. 마틴","rating":null}
                     ↑ status 키가 아예 없다
```

`repo.create()`는 **값이 `undefined`인 속성을 아예 만들지 않는다.** 그래서 엔티티의 `default`가 정상 적용된다. 안전했다.

### 3. 데이터가 있으면 기본값 없는 NOT NULL 컬럼은 추가할 수 없다

5단계 노트의 질문에 대한 답. 사본으로 실험했다.

```text
❌ NOT NULL constraint failed: t.memo
   code: SQLITE_CONSTRAINT_NOTNULL
```

복사해 넣을 값이 없으니 제약에 걸린다. **빈 테이블이었다면 넣을 행이 없어서 그냥 성공한다.** 즉 개발 중엔 잘 되다가 데이터가 쌓인 운영에서 터지는 종류의 문제다.

### 4. SQLite의 컬럼 추가는 `ALTER`가 아니다

이것도 5단계에서 "확인해봐야 한다"고 남겨둔 것. `migration:generate`가 만들어준 SQL은 이랬다.

```sql
CREATE TABLE "temporary_reading_records" (... 새 컬럼 포함 ...)   -- ① 새 테이블
INSERT INTO "temporary_reading_records"(...) SELECT ... FROM "reading_records"  -- ② 복사
DROP TABLE "reading_records"                                        -- ③ 원본 삭제
ALTER TABLE "temporary_reading_records" RENAME TO "reading_records" -- ④ 이름 바꿔치기
```

컬럼 하나 추가하는데 테이블을 통째로 다시 만든다. 1번 사고가 그렇게 큰 피해로 이어질 뻔한 이유도 이것 때문이다.

### 5. `save()`는 `undefined`는 빼지만 `null`은 반영한다

5단계에서 "`save()`가 `undefined`인 속성을 UPDATE에서 제외한다"를 배웠다. 그럼 `null`도 그럴까? 그렇다면 "별점 지우기"가 조용히 실패한다.

테스트로 확인했더니 **`null`은 정상적으로 `SET rating = NULL`로 나간다.** 의도대로 동작했다.

다만 이건 짐작으로 넘어갈 수 없는 부분이라, 테스트를 두 겹으로 만들었다. 5단계에서 배운 그대로다.

```ts
expect(returnedRecord.rating).toBeNull();          // 응답이 맞는가
const reloaded = await service.findOne(id);
expect(reloaded.rating).toBeNull();                // DB도 맞는가
```

### 6. e2e 테스트 3개가 깨졌고, 그게 맞는 동작이었다

필드를 추가하니 e2e 3개가 실패했다.

```text
Tests: 3 failed, 10 passed, 13 total
```

5단계에서는 저장소를 배열에서 SQLite로 **통째로 갈아치웠는데도** e2e를 한 줄도 안 고쳤다. 겉으로 드러나는 약속이 안 바뀌었기 때문이다.

이번엔 반대다. **응답에 필드가 늘었으니 계약이 실제로 바뀌었고**, e2e가 그걸 잡아냈다. 테스트가 제 일을 한 것이다.

- 5단계: 구현이 바뀜, 계약은 그대로 → 테스트 수정 없음
- 6단계: 계약이 바뀜 → 테스트 수정 필요

e2e 테스트가 "구현"이 아니라 "약속"을 검사한다는 게 양쪽 방향으로 확인됐다.

### 7. 단위 테스트의 `synchronize: true`를 걷어냈다

5단계 노트의 첫 번째 숙제. 전에는 이랬다.

```ts
TypeOrmModule.forRoot({
  type: 'better-sqlite3',
  database: ':memory:',
  entities: [ReadingRecord],
  synchronize: true,        // 엔티티를 보고 테이블을 만든다
}),
```

즉 **마이그레이션이 잘못돼 있어도 단위 테스트는 통과한다.** 테스트가 검사하는 스키마와 실제로 앱이 쓰는 스키마가 다른 것이다.

앱 설정을 그대로 가져다 쓰고, 메모리 DB만 못박는 방식으로 바꿨다.

```ts
TypeOrmModule.forRoot({
  ...dataSourceOptions,     // 엔티티 목록도 마이그레이션 목록도 앱과 같은 것
  database: ':memory:',     // 실수로 개발 DB에 붙지 않도록 여기서 못을 박는다
  migrationsRun: true,      // 빈 메모리 DB라 마이그레이션이 테이블을 만들어야 한다
}),
```

`database: ':memory:'`를 굳이 다시 쓴 이유가 있다. `dataSourceOptions`의 DB 경로는 `process.env.DATABASE_PATH ?? 'readlog.sqlite'`인데, 단위 테스트는 그 환경 변수를 설정하지 않는다. **그대로 두면 테스트가 개발용 파일 DB를 지웠다 만들었다 한다.**

## 어떻게 확인했나

```bash
# 1. 마이그레이션 생성 — 현재 DB(마이그레이션 1번까지 적용됨)를 기준으로
pnpm migration:generate src/migrations/AddStatusAndRating

# 2. 중복 실행 시 데이터 손실을 사본으로 검증
#    status='finished', rating=5  →  up() 한 번 더 실행  →  'want_to_read', null

# 3. 기본값 없는 NOT NULL 컬럼 추가를 사본으로 검증
#    → SQLITE_CONSTRAINT_NOTNULL

# 4. 엔티티 default 유무에 따른 INSERT문 차이 확인 (임시 스크립트)
#    default 있음 → status를 값과 함께 INSERT
#    default 없음 → status에 NULL 명시 → 실패

# 5. 전체 검증
pnpm format
pnpm lint
pnpm build       # 타입 검사
pnpm test        # 15 passed  (10 → 15)
pnpm test:e2e    # 18 passed  (13 → 18)

# 6. 실제 서버로 확인
pnpm start
curl localhost:3000/reading-records
curl -X POST ... -d '{"title":"...","author":"...","status":"abandoned"}'
# → 400 "status must be one of the following values: want_to_read, reading, finished"
```

기존 기록 1건이 마이그레이션 후 `status: "want_to_read"`, `rating: null`로 나온 게 이번 단계의 증거다. **데이터를 지우지 않고 스키마를 바꾼 것**이 5단계와 달라진 점이다. (5단계에서는 이력이 꼬여서 DB 파일을 지우고 다시 만들었다.)

## 아직 모르는 것

- **`status`와 `rating` 사이의 도메인 규칙이 없다.** 지금은 `want_to_read`인데 별점 5점을 줄 수 있다. 읽지도 않은 책에 별점이 있는 게 말이 되나? 이런 "필드 사이의 규칙"은 DTO 데코레이터 하나로는 표현이 안 되는데, 어디서 검사해야 하나 — 서비스? 커스텀 validator?
- `status`를 `finished`로 바꿀 때 완독일이 자동으로 기록되면 좋겠는데, 그런 "상태가 바뀔 때 함께 일어나는 일"은 어디에 두나?
- 마이그레이션 클래스를 배열에 손으로 등록하는 방식 — 5단계에서 남긴 질문이 그대로다. 이제 2개가 됐다.
- 운영 배포에서 `ts-node` 없이 마이그레이션을 실행하는 방법도 그대로 숙제다. 이번에 `migrationsRun`을 껐으니 **더 중요해졌다.** 자동 실행이 없으니 배포 절차에 반드시 들어가야 한다.
- 목록 조회에 정렬·필터가 없다. `status`가 생겼으니 "읽는 중인 책만 보기"가 자연스럽게 필요해진다.
- 엔티티가 그대로 API 응답이 되고 있다. 지금은 숨길 필드가 없어서 문제가 안 보이지만, 언제 분리해야 하나?
